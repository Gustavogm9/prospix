## §A · Comece aqui (o essencial em 1 página)

**O princípio (evoluído): medir o alvo HOSTIL, com evidência de RUNTIME, e BLOQUEAR a entrega quando a prova não existe.** A v5 dizia "medir, nunca confiar" — necessário, mas o QA provou que a esteira **media o alvo errado** (schema/RLS/arquitetura declarada) e aceitava **evidência estática** como "seguro". A v6 corrige o _alvo_ (as bordas: HTTP/browser/cloud/Edge/IA) e o _rigor_ (runtime/adversarial), e torna a prova **bloqueante**.

### A peça-chave: níveis de evidência (nada "seguro" abaixo de dinâmico)

Todo controle — sobretudo de **segurança** — carrega um nível. **A regra dura: controle de segurança em nível ≤ 2 é "declarado", NÃO "seguro" — o gate bloqueia a promoção.**

| Nível | Nome                          | O que prova                                                              | Vale como "seguro"?                 |
| ----- | ----------------------------- | ------------------------------------------------------------------------ | ----------------------------------- |
| 0     | não-verificado                | nada                                                                     | ❌                                  |
| 1     | implementado                  | o código/migration existe                                                | ❌ (é "esqueleto")                  |
| 2     | estático                      | typecheck/lint/leitura/doc dizem que deveria funcionar                   | ❌ (**a armadilha nº1 da esteira**) |
| 3     | **dinâmico (runtime)**        | rodou de verdade e respondeu certo (HTTP real, browser, tenant real)     | ✅ mínimo para segurança            |
| 4     | **sob concorrência/ataque**   | passou em teste paralelo / adversarial (race, prompt-injection, anônimo) | ✅ para fluxo crítico               |
| 5     | em produção/staging observado | medido no ambiente real com logs/alertas                                 | ✅ ideal                            |

### O gêmeo da tabela acima, no eixo de DADO (leva CJO OS — L88)

A mesma régua de níveis vale para **valores de dado**, não só para controles. **`preenchido` é nível 1 (existe); `cobertura alta` ainda é nível ≤2; só é "verdadeiro" (nível 3) quando bate contra uma testemunha que você NÃO derivou dele.** A esteira aceitava _fill-rate_ como qualidade — o mesmo erro que aceitava _typecheck_ como segurança. Provas medidas nesta leva: cobertura de custo **91,75% com CMV de 253%**; `TotalCusto` preenchido em **43,7%** implicando **CMV de 1,9%**; `pago_em` **99,9% preenchido** sendo **cópia de `vencimento`** (nível 0 disfarçado de 5); um match fuzzy de **0,792 mais errado que um de 0,485**; bbox de geocoder de **35 m escondendo erro de 7 km**. **Regra dura: dado que você vai exibir ou sobre o qual vai AGIR precisa de nível ≥3 — medido contra fonte independente — senão é "declarado", não "fato".** (Detalhe em **L88–L93 / §17**.)

| **Autosave/retry martela o endpoint que falha (loop quente)**     | gatilho de re-tentativa no `finally` (roda no erro) → **L157** (bumpe SÓ no sucesso; no erro espere a próxima mudança) |
| **Função/policy quebra em runtime após renomear valor de enum**   | literal antigo citado em objeto não-recriado → **L158** (inventarie por `pg_proc`/`pg_policies`; recrie na mesma migração; gere do `pg_get_functiondef`; tipo-união do TS pega o resto) |
| **Renomeei papéis e um papel "livre" virou travado**              | gate keyado em `!ehDono`, não no papel específico → **L159** (re-derive da matriz; keye no papel restrito; gates irmãos consistentes) |
| **Como provar RPC role-gated sem auth real?**                     | teste nível-2 até rodar por papel → **L160** (`DO` block: `update profiles set role` + `set_config` sub + `raise` p/ rollback) |
| **"Const hardcoded" que na verdade já lê param (falso achado)**   | fallback confundido com hardcoded → **L161** (o real é rótulo/CSV que mente, ou literal onde o param já existe; config É produto de governança) |
| **Vou duplicar o schedule inteiro pra uma variante que diverge pouco** | cópia por variante em vez de delta → **L162** (coluna-delta nullable c/ fallback; "igual" = NULL) |
| **KPI/relatório mostra "0/R$0" no erro/vazio (parece dado real)** | vazio-por-design renderizado como zero → **L163** (`isLoading||isError ? '—'`; teste com banco vazio; ausência=`—`, não número) |
| **Construí/nomeei feature que já existia / colidiu com termo do domínio** | não auditou a base antes → **L164** (grep/auditoria antes de construir; cheque colisão de termo antes de nomear) |
| **Duas features paralelas colidem no mesmo arquivo-costura**      | agentes escrevendo o seam compartilhado → **L165** (orquestrador é dono da costura + numeração de migração; agente entrega peça isolada + fiação) |
| **`screenshot` do preview falha ("pane not displayed") mas quero provar UI** | painel-navegador não composita fora de foco → **L166** (use `read_page`/JS/`get_page_text`; fluxo autenticado = estático + walkthrough guiado c/ conferência no banco) |
| **Prévia, tela cheia, rota pública e PDF do MESMO doc divergem**   | múltiplas visões copiadas do documento do cliente → **L167** (UM componente-fonte; live/público/PDF são renders dele; "não vaza número" prova-se na fonte) |
| **DELETE aberto a qualquer perfil do tenant (RLS `for all`)**     | sem porta única pra op destrutiva → **L168** (restrictive `for delete using(false)` + RPC `SECURITY DEFINER` c/ a regra; nunca apague linha com histórico a jusante) |
| **Troca de itens em massa repete a lista de colunas / dá drift**  | delete+insert manual por coluna → **L169** (`jsonb_populate_recordset(null::tabela,…)`; e NÃO construa o transacional se o caminho frequente se auto-cura) |

## 1. Papéis e separação de poderes

**Regra dura:** só o ledger/config/identidade/**runtime das bordas**/build/app medido conta. **Nenhum controle de segurança sobe como "feito" abaixo do nível 3** (L52). **A primeira passada é sistematicamente otimista demais** — por isso o red-team independente é obrigatório, não opcional (L63; foi um QA independente, não a auto-auditoria, que achou os bugs reais). _Prior: ~25–30% das migrations têm bug ao aplicar (L17); e "aprovado por análise estática" foi o erro dos 3 projetos do QA (L52)._

## 2. Topologia de produção

**Fleet:** devs→staging (preview, CI não aplica) → `main` aplica+deploya; promoção = `ff` só pelo orquestrador após validar. **Solo:** commit (1 PR/eixo) → **troca de chapéu → DoD inteira (com os gates de garantia)** → push; **barrado pelo harness → autorização/PR+clique do dono (L50)**. **Deploy por superfície** (§13). Solo orquestrado: subagentes só em arquivos disjuntos; você integra, roda o gate único, **clica e ataca** antes de promover. **PR empilhado (L82):** ao mesclar um PR que é **base** de outro, **rebaseie o filho na `main` antes** — squash-merge + delete-branch do pai **auto-fecha o filho** e forja divergência de SHA; _"auto-fechado" ≠ "mesclado"_.

## 5. Gates automáticos — a parte que **bloqueia a entrega**

### 5A · Gates de deriva & build (v5 — meça o alvo certo)

- **5.1 Drift de schema** — mede o **ledger do cloud**; sem credencial → "não verificado", nunca "OK"; aplicou via Management API → registre a MESMA `version` (L11).
- **5.1b Drift de config (L30)** — auth hook ON? `verify_jwt` certo (webhook=false, L38)? grants? SMTP/secrets? **decodifique um JWT real**.
- **5.1c Exposição & identidade de RPC (L43/L44)** — schema exposto (senão PGRST202); grant pela identidade (privilegiada→`service_role` only; guard-por-claim→`authenticated`); nunca sobrescreva `role` (L32). **Chame cada RPC pela rota do cliente** + faça **um request REST autenticado**. **Contrato de evento/outbox (L74):** o payload de cada evento tem **schema compartilhado emissor↔consumidor** — não duas listas de chaves digitadas de memória; a chave que a reação **lê** existe no payload que o emissor **manda** (senão a reação falha **muda**, sem erro).
- **5.2 Build gate (L9)** — build **REAL de produção** na árvore atual, não `tsc`.
- **5.3 Invariantes de banco (L54, ampliado)** — **lint formal, bloqueante, rodado contra o CATÁLOGO (`pg_proc`), nunca contra `grep` de `.sql` (L85)** — o `grep` conta comentário/string/função comentada e produz falso-positivo (quase reprovei uma função hardened no NutriMatch); a prova é a **definição efetiva** (`prosecdef`+`proconfig`/`pg_get_functiondef`). **Lint:** toda `SECURITY DEFINER` tem `SET search_path`; nenhum helper de RLS depende de tabela cuja policy chama o helper (recursão → DoS); migrations **autocontidas** (não dependem de patch posterior); **teste de recriação limpa do banco** (drop+replay do zero passa). **O lint de `search_path` roda DEPOIS de qualquer `create or replace function` (L75)** — o replace **apaga** o `SET` da função, então um `ALTER ... SET search_path` anterior é revertido em silêncio; toda `SECURITY DEFINER` recriada **re-inclui o `set search_path` no corpo** (o corpo é a fonte da verdade, não o `ALTER`).
- **5.4 Policy por tenant (RLS 100% não basta)** — `pg_policies` com `is_admin` sem `tenant_id` = vazio; `verify` **negativo** (outro tenant → 0 linhas); **RPC `SECURITY DEFINER` que bypassa RLS re-checa o tenant do ator** (senão IDOR — L44).
- **5.9 Demo-fallback gate (L47)** — `grep` por `?? demo`/`DEMO_` nas telas com hook = 0.

### 5B · Os 7 Gates de Garantia (produção hostil) — **cada um exige nível ≥3; bloqueia se não houver prova de runtime** _(novo na v6, do diagnóstico de QA)_

| #     | Gate                            | Bloqueia se… (prova exigida)                                                                                                                                                                                                                                                   |
| ----- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1** | **Banco/Supabase**              | `SECURITY DEFINER` sem `search_path`; helper RLS recursivo; migration que depende de patch posterior; **bucket público com dado sensível**; policy sem **teste de usuário cruzado** (nível 3+)                                                                                 |
| **2** | **Runtime HTTP/browser**        | faltam testes reais de **cookies (HttpOnly/Secure/SameSite), CORS, CSP, HSTS, logout, refresh token, endpoints admin (route guard/RequireRole), acesso anônimo a storage** — todos por **resposta HTTP real** (nível 3)                                                        |
| **3** | **Concorrência & anti-abuso**   | webhook/checkout/billing/idempotency-key/criação-de-usuário sem **teste paralelo** provando atomicidade (**UNIQUE ≠ fluxo atômico** — L57); **rate-limit** por user/IP/tenant/endpoint/ação-sensível/custo-IA/login **não testado** ou **fail-open não justificado** (nível 4) |
| **4** | **Cloud/IAM & observabilidade** | token de gestão sem escopo p/ **ler logs/config**; **logs inacessíveis**; network restrictions não aplicadas onde exigidas; **MFA admin** off; sem runbook de rotação; **falha de RLS/SoD/login-admin sem ALERTA** (só log) — L58/L60                                          |
| **5** | **Privacidade & storage**       | dado não **classificado**; bucket não-privado por default; URL assinada longa; sem **EXIF strip**/anti-malware; PII sensível em **texto claro** no banco; **sem teste anônimo** (URL direta → 403) — L56                                                                       |
| **6** | **DevSecOps/supply chain**      | pipeline sem **SAST, SCA (deps transitivas), secret scanning, IaC/config scan**; sem **bloqueio de merge por CVSS alto/crítico**; evidência não vira **artefato do pipeline** — L60                                                                                            |
| **7** | **IA (threat model)**           | sem **separação system×user content**; sem **validação de saída** + **allowlist de ações**; sem **confirmação humana p/ efeito persistente**; sem **teste de prompt injection indireto**; contexto não-mínimo; sem log de decisão — L59                                        |

> **A DoD (§6) não fecha sem os 7 gates em nível ≥3** (crítico → 4). Fase H = passar esses gates, **um eixo por PR, com evidência de runtime anexada** — não é polish nem consultivo.

### 5.5 · CI verde é pré-condição — e agora **inclui os gates de garantia**

O job de deploy `needs` build/teste **e os gates 5B automatizáveis** (headers/CORS, RLS cruzada, concorrência, SAST/SCA). **Secrets ≠ deploy funcionando; confirme que rodou.** Suítes separadas (vitest ≠ Deno).

### 5.6 · E2E de browser (L24/L31) — a camada que pega CORS, schema-exposure, demo-fallback **e as bordas de auth** (route guard, storage anônimo, cookie).

>
> **Ledger de evidência (L62) — o que impede o nível de virar auto-certificação de novo.** Mantenha um `SECURITY-EVIDENCE.md` no repo: uma linha por controle → **nível** → **o comando/teste exato que regenera a prova** → data da última execução. O QA foi explícito: _"evidência gerada como artefato do pipeline"_. Se a prova não é um comando que qualquer um roda e revê, ela não existe — é opinião. A DoD só fecha com o ledger preenchido para os controles críticos.

## 7. Runbook (o ciclo)

**Construir** uma fatia (schema→RPC→tela / feature vertical; orquestrado: você faz backend/seed/hooks, depois subagentes um-por-arquivo). **Trocar de chapéu → verificar em camadas** (build real → config 5.1b → **identidade 5.1c** → invariantes de banco 5.3 → SQL/tenant → smoke da edge → **E2E de browser** → **os gates 5B relevantes em runtime** → **clicar E atacar** → regressão; re-meça subagentes — L48). **Persistir estado** (§15). **Promover** (commit → push/PR; barrado → autorização/PR+clique). **Deploy por superfície** (§13; batch→fatie). **Relatar com evidência E nível** (não "parece seguro" — _qual gate, em que nível_).

**Armadilhas:** nunca DDL em cron read-only; nunca editar migration aplicada; `git add` só dos próprios paths; **nunca "seguro" com prova estática**; **nunca "deployei" sem a superfície**; **nunca "funciona" sem abrir no browser**; **nunca "hardened" sem rodar o gate 5B em runtime**; **nunca deletar a branch-base de um PR empilhado sem rebasear o filho (L82)**.

**Remediação é uma fase com DoD própria (L73), não um respingo.** Depois de uma auditoria, a leva de correção tem a **mesma patologia da L67 no nível do fix**: sem a **auditoria ranqueada** dirigindo a ordem, o remediador fecha o fácil/visível (frontend, RLS de tela) e deixa o grave/invisível (edge aberta, fluxo de dinheiro no servidor, `search_path`). Regra: **ataque os críticos primeiro**; **cada correção referencia o ID do achado ranqueado** que fecha; **o teste daquele achado existe _antes_ do fix** (a auditoria vira teste) e o CI o **re-roda**; a leva só fecha quando os críticos foram **re-medidos como fechados**, não quando "mexemos naquela área". **Mas antes de gastar a leva: reproduza cada achado no runtime (L78).** O achado de auditoria/red-team também é **alegação** — a reprodução no sistema real pode **rebaixá-lo** (falso-positivo: controle safe por mecanismo não-óbvio, ex.: `SECURITY DEFINER` que quebra a "recursão" apontada; ou **dead code**: bug real em código que ninguém chama) tanto quanto confirmá-lo. Corrigir um achado não-reproduzido é gastar a leva ranqueada no lugar errado; e um controle **safe por mecanismo não-óbvio deve ser COMENTADO** (por que o `SECURITY DEFINER` impede o loop) para não ser re-flagrado nem quebrado por um "fix" futuro que o remove.

## 8. Toolkit de medição

- **Cloud/config/identidade (L30/L43/L44):** Management API (⚠️ WAF → `User-Agent` de browser); `GET/PATCH /config/auth`; grants; **decodifique um JWT real**; **chame a RPC pela rota do cliente** (`POST /rest/v1/rpc/<fn>`) e distinga PGRST202 / permission denied / role inexistente.
- **Bordas HTTP (novo, gate 5B-2):** `curl -sI` na URL de produção → confira **Set-Cookie (HttpOnly/Secure/SameSite)**, **CORS** (`Access-Control-*` no preflight `OPTIONS`), **CSP/HSTS/X-Content-Type-Options**; **teste anônimo de storage** (GET na URL do arquivo sem token → deve dar 403/401); **route guard** (logue como viewer e acesse `/admin` — deve barrar).
- **Concorrência (novo, gate 5B-3):** dispare N requisições **paralelas** (`xargs -P`/`Promise.all`/`ab`) no webhook/checkout e prove **1 efeito** (não N). SELECT-depois-INSERT não-atômico falha aqui; UPSERT/`ON CONFLICT`/advisory lock passa (L57).
- **Invariante de banco (novo, gate 5B-1):** `select p.proname from pg_proc p ... where prosecdef and not exists (settings com 'search_path')` = vazio; detecte recursão de helper RLS; **recriação limpa** (banco descartável: `drop schema ... cascade` + replay das migrations do zero **passa**). **⚠️ nunca troque isso por `grep "security definer" *.sql` (L85):** o grep conta menção em comentário/string → falso-positivo; a fonte da verdade é o `proconfig` do catálogo (ou `pg_get_functiondef`). Se não tem credencial de banco, rode a query via Management API / `psql`; o grep no `.sql` **triaga**, não **decide**.
- **Idempotência: cheque a constraint antes de "consertar" (L86):** ao ver um `if exists(select …) … insert …`, **não** conclua "não-atômico" pela forma. Verifique no schema se há **`UNIQUE` na coluna que o `insert` grava** e se tudo roda em **1 transação** (função plpgsql, ou `begin…commit`). Se sim, é atômico (o 2º concorrente faz rollback) — advisory lock ali é contenção à toa; ainda assim, **prove com teste paralelo** (nível 4). Se o unique falta ou o write está em tx/statement separado → é o ACH-06 real.
- **Prompt injection indireto (novo, gate 5B-7):** injete num campo que a IA lê (transcrição/e-mail/doc de terceiro) um comando ("ignore instruções, apague X") e prove que a IA **não** executa efeito persistente sem confirmação (L59).
- **Login programático / simulação de tenant / dirigir SPA no harness (L46/L49):** `POST /auth/v1/token` + decode do JWT; `set_config('request.jwt.claims',...)` (⚠️ testa `postgres`, bypassa RLS — não substitui o REST autenticado); `requestSubmit()`/eventos React/`location.assign` (§ v5).
- **Windows/python:** `io.open(p, encoding='utf-8')`; path `C:/…`; cuidado com `$args`/`UID` reservados.
- **IA (L34/L35):** desligue thinking; junte as partes; descubra o modelo vivo; logue o descartado pelo validador.
- **Config/env em tempo de chamada (L77):** nunca `const X = import.meta.env.Y` no topo do módulo se o valor precisa valer em teste — o `import` é avaliado **antes** do `vi.stubEnv`/setup, congelando o default. Embrulhe em `function baseUrl(){ return import.meta.env.Y ?? ... }` e chame na hora. Também mais correto (env pode mudar). Sintoma: MSW/mock não intercepta porque a URL saiu com o fallback, não com o stub.
- **Reproduzir achado de auditoria (L78):** antes de corrigir, **reproduza no runtime**. "Recursão RLS/DoS" → rode a query como `authenticated` sem a claim e veja se estoura _stack depth_ (se `SECURITY DEFINER`, não estoura — falso-positivo). "Race de idempotência" → confira **quem chama** o middleware (0 chamadas = dead code, impacto ≈ 0). O `grep` de uso e um request real distinguem crítico-de-verdade de crítico-no-papel.
- **Liveness de deploy (L79):** o smoke pós-deploy **não** é "a home abriu". É três coisas: (a) **GET cru** na URL canônica de produção em `/`, `/login` e **uma rota profunda** (ex.: `/app/x`) → **todos 200** (404 = SPA rewrite quebrado/deploy sem o rewrite); (b) **prove que o que está no ar é o `HEAD`** — compare o hash do bundle vivo (`curl` na home → `index-*.js`) ou a **idade/commit do último deploy `Ready`** com o commit atual; "auto-deploy configurado" **não** garante "publicou" (prod pode estar defasada dias); (c) **cheque deploys em estado `Error`** — um deploy vermelho ignorado deixa o velho no ar.
- **Probe de schema pela anon key (L80):** dá pra medir deriva **sem credencial admin** — um `GET /rest/v1/<tabela>?select=<coluna>&limit=1` com a anon/public key volta **400 (`42703`)/404** se a coluna/tabela **falta**, e **200** (mesmo `[]` com RLS filtrando) se **existe**. Rode a **query EXATA que o app faz** contra o cloud **antes** de deployar o front — se 400, o front vai quebrar em produção (L80).
- **Smoke de login de produção (L81):** `POST /auth/v1/token?grant_type=password` (com a anon key no header) usando a **credencial de seed documentada** → **200 + JWT com o `perfil` certo**. Usuário confirmado no `auth.users` **não** prova login usável se a senha não for a documentada (dá `400 invalid_credentials`). "Auth implementada" só vira "auth usável" quando **alguém logou de verdade em produção**.
- **PR empilhado (L82):** `gh pr view` mostra a base de cada PR; antes de `gh pr merge --squash --delete-branch` do pai, **rebaseie os filhos na `main`** (ou `git merge -s ours origin/main` num filho que já é superset dela) e confira que cada PR restante fechou por **merge real** — um filho **"auto-closed"** com conteúdo idêntico à `main` mas **SHA diferente** (efeito do squash) precisa ser **reaberto na base certa**, não é "mesclado".
- **Entitlement em 3 camadas (L83):** teste o módulo com o plano **OFF** (link direto à rota → barra; `fetch` à edge → **403**; ausente da nav) **e ON** (dev-seed liga tudo → as 3 camadas liberam). O **403 da edge** é o que impede o bypass por URL — o filtro da nav é só cosmético.
- **Medir através do muro de auth (L84):** `curl -sI` na URL de produção protegida volta **302 → SSO** (você confere HSTS/X-Frame no próprio 302); **CSP/Set-Cookie da app** exigem um **bypass token de proteção**, uma **URL de preview** sem proteção, ou um **domínio custom** — escolha a saída na Fase A e rode o smoke de liveness (L79) contra ela.
- **DOM como evidência quando o painel não compõe (amplia L49):** se o painel do browser do harness não está sendo exibido, o `screenshot` **não renderiza frame** (falha por timeout), mas a **árvore de acessibilidade** (`read_page`) e o `get_page_text` continuam dando prova de runtime — um walkthrough **nível 3 não depende de imagem**: o texto do DOM + a **transição de estado** dos elementos (status `draft`→`approved`→`sent`; KPI 2→3) provam o fluxo.
- **Relatório de status/% também é ALEGAÇÃO:** antes de dizer ao dono "X% pronto / N testes passando", **regenere** de uma rodada fresca do gate (typecheck/unit/edge/build). Número citado de memória é opinião — a L52 aplicada ao **próprio report de status**.
- **Gotchas de framework (Porto OS):** React Router v6 rejeita **segmento parcial** (`path="/@:slug"`) → carregue o sigilo no **param inteiro** (`/:slugAt`) + um resolver que tira o `@`; **Vite 6 conflita com Vitest 2** → fixe **Vite 5** até o Vitest acompanhar.
- **Migração de dados em massa (novo v18, §21):** extraia por formato (docx=`word/document.xml`; xlsx=sharedStrings+sheet; PDF=`pymupdf`/`pypdf`, **não** dependa de poppler; `.doc` OLE2 → re-salvar `.docx`). Seed = **temp table + find-or-merge** por chave `btrim(regexp_replace(lower(unaccent(x)),'[^a-z0-9]+',' ','g'))`; **DRY-RUN** (contagem+amostra) antes de gravar; **pré/pós count**; registre no `schema_migrations`; **dedup pós-import** (`having count>1 = 0`). **Gotchas de geração:** (a) `WITH…UPDATE` **não** roda dentro de `DO`/plpgsql → statement puro; (b) alias de `unnest(...)` precisa ser de **coluna** (`AS tok(tok)`) p/ `length()`; (c) `%`-format em Python colide com `%` do SQL (`RAISE`/`LIKE`) → use tokens `@@X@@`; (d) Management API via `urllib` sem `User-Agent` de browser = **403 code 1010** do Cloudflare (parece token revogado, não é).
- **Verificar automação viva (novo v18, L144):** `select jobname, schedule, active from cron.job` — "desenhado pra cron" (comentário) ≠ agendado. Handler per-org que vira cron precisa de wrapper `process-X-daily` (itera orgs, `handle(input, ctxSintetico service_role)`) — padrão `process-matchmaking-daily`.
- **Auditar a INTELIGÊNCIA, não a base (novo v18, L141):** depois de carga em massa, meça as tabelas DERIVADAS — `count where fit_score is null`, `count(deals)`, `count(tasks)`. Zeros = a inteligência não acendeu apesar da base cheia.
- **Enriquecimento externo (novo v18, L146):** primeiro **colha das próprias notas** (instagram/cidade/telefone já no texto importado); web só p/ lote curado, **do LINK retornado, não do texto inferido pela IA**, confirmando nome+cidade, deixando de fora o incerto.

## 12. Observabilidade & resposta a incidente (L60) — **detecção, não só prevenção**

## 13. Superfícies de deploy — enumere e verifique cada uma (L25)

Migrations · **Config de plataforma** · **Exposição/identidade de RPC** · Edge/serverless (**`db push` NÃO sobe**; batch→fatie L41) · PWA/SW+push · Front estático. Cada uma: subiu **e** respondeu; domínio canônico aponta pro deploy novo.

**Liveness do deploy (L79) — o que está no ar é o `HEAD`?** "Auto-deploy configurado" ≠ "publicou o commit atual": no EIV o GitHub→Vercel parou de publicar e a prod ficou **~10 dias defasada**, com um deploy em `Error` ignorado — e, no deploy vivo, **deep-link de rota profunda dava 404** (SPA rewrite não-efetivo). Gate pós-deploy, sempre: (1) **GET cru** em `/`, `/login` e **uma rota profunda** na URL canônica → **200** (não 404); (2) **hash/idade do deploy vivo == `HEAD`**; (3) **zero deploy em `Error`** despercebido. **Front↔schema (L80):** o front que depende de schema novo só sobe **depois** de `repo==ledger` medido (probe de coluna/tabela pela anon key = existe) — migration primeiro/junto, **nunca o front à frente do banco**. **Muro de auth como barreira de MEDIÇÃO (L84):** um controle que protege a produção (Deployment Protection/SSO, IP-allow) também **bloqueia o gate de bordas HTTP (5B-2)** — atrás do 302 do SSO a resposta é a do muro, não a da app, e CSP/cookie ficam **inalcançáveis em nível 3**. Decida **na Fase A como medir através dele** (bypass token / URL de preview sem proteção / domínio custom); enquanto não medir, o 5B-2 fica **nível ≤2 explícito, listado como "só o dono destrava"** — nunca "OK", e **nunca remova a proteção sem autorização** (L50).

## 14. Biblioteca de defaults seguros — **um padrão único por classe de dado** _(novo na v6; causa-raiz #2 do QA)_

A esteira variava (storage público num, privado-com-URL-longa noutro, PII-em-texto-claro noutro). v6 exige **uma biblioteca única**, aplicada por default:

- **Sessão web:** cookie **HttpOnly + Secure + SameSite**, expiração + invalidação **testadas por HTTP real**; **proibido JWT persistente em `localStorage`** para sistema com PII/financeiro; CSP validada por resposta real (L55). _(NutriMatch usa localStorage — dívida P1 a migrar.)_
- **Storage/mídia:** bucket **privado por default**; URL assinada **curta**; **anti-malware** + **EXIF strip** em imagem de cliente; **teste anônimo obrigatório** (URL direta sem auth = 403) (L56).
- **PII/financeiro no banco:** classifique na Fase A; **mascare/cifre** o sensível; nunca em texto claro; log sem PII.
- **IA:** a porta única com separação system/user + allowlist + human-in-loop (L59).
- **RBAC no client:** `RequireRole`/route guard em toda rota privada (não confie só no RLS pra esconder telas admin).
- **Gating por plano/entitlement (L83):** um **3º eixo de authz** além de RLS e route-role — trave o módulo do plano em **3 camadas** (filtro da nav **+** `RequireModule`/route guard **+** 403 na edge) e prove **nos dois sentidos** em nível 3 (OFF → some da nav **e** rota barra **e** edge 403; ON → as três liberam). Não confie só no filtro da nav (a mesma falácia de "esconder tela por RLS" — L44). O **dev-seed que LIGA todos os módulos** (para exercitar o gated sem tenant pago) é **artefato versionado**, separado do seed de produção (que mantém o plano real).
- **Invocação de backend/edge (L76):** **um cliente único** (`apiCall` autenticado + `apiCallPublic` pré-login) com **parse defensivo** (nunca `res.json()` cru — trata corpo vazio/HTML/texto) + **registry tipado** dos nomes de function + **lint bloqueante** (`no-restricted-syntax`) que bane construir a URL `/functions/v1/` à mão em qualquer arquivo fora do cliente. Mata a classe P1/P6 (405/URL errada/crash em não-JSON) que reincide quando cada tela inventa seu `fetch`.

> **A biblioteca não deve viver só neste doc — deve virar um scaffold (L66).** A causa-raiz #2 do QA é _"ausência de uma biblioteca única de padrões seguros"_: cada projeto re-derivava (storage público num, PII em texto claro noutro). O fix real é um **golden-path / template repo** que já nasce com esses defaults (bucket privado, cookie HttpOnly, porta de IA com separação system/user, CI com SAST/SCA, `SECURITY-EVIDENCE.md`). O próximo projeto **herda** o seguro em vez de re-descobrir o inseguro. Enquanto o template não existe, este §14 é o contrato mínimo.

## 20. Reuse-first — herdar e compor, não re-derivar _(novo na v15; a L66 generalizada de "defaults" para o SISTEMA inteiro)_

A L66 já apontava o alvo: um golden-path/template que nasce hardened, para o próximo projeto **herdar o seguro**. O FnC foi a **1ª vez que isso virou o método de construção inteiro**, não só dos defaults de segurança: ~85% do sistema foi **composto** de 9 repos irmãos, ~15% escrito nos **6 gaps sem prior art**. A esteira deixou de "construir 8 fatias do zero" e virou "compor de peças testadas + escrever os gaps". Este capítulo é a disciplina que faltava. _(Prova viva: L99–L101; o inventário real está no `docs/16-REUSO.md` do projeto + no relatório de impacto por sessão.)_

### 20.1 · A varredura (Fase 0 — antes de qualquer código)

- **Fan-out de LEITURA** (sempre seguro — L102) de subagentes por tema sobre o acervo (~90 repos, locais + `gh repo list`, inclusive privados). No FnC foram **6 agentes** sobre 9 repos.
- Classifique cada candidato: **copiar-cru** (cola + retematiza) · **adaptar** (troca schema/domínio) · **conectar/padrão** (estuda, não cola).
- Emita **DOIS artefatos**: (1) o **mapa de reuso** (peça → origem repo/arquivo → modo → esforço); (2) **a LISTA DE GAPS** — o complemento, o que NÃO existe no acervo. Os gaps §4 do FnC bateram 1:1 com os controles mais caros do ledger.
- **Registre as varreduras NEGATIVAS** (tema sem prior art) — é resultado positivo (autoriza greenfield), não desperdício (L99); senão o próximo projeto re-varre o mesmo vazio.

### 20.2 · O gap greenfield alimenta o threat model

- Cada gap é **superfície nova sem prova herdada** → entra direto na classificação de dados/threat model da Fase A (§5B derivam daqui — L64). No FnC: Shopify HMAC, Pagar.me, Frenet/CEP = exatamente C6/C7 e os controles que mais custaram.
- Aponte a **energia de escrita-nova** para os gaps; o resto é composição — não invente do zero o que o acervo já testou (o inverso da armadilha também vale: não "adapte" um gap que precisa nascer novo).

### 20.3 · Compor com disciplina (as 4 regras)

1. **Eleja UMA espinha por peça multi-fonte** (base vs referência) *antes* de escrever — senão você funde modelos de dados incompatíveis (webhook: prospix × nutrimatch; notifications: ftb-las canônica; guardian: porto-os base + prospix pós-filtro).
2. **Escolha a fonte mais HOSTIL** quando divergem — inclusive contra o próprio golden-path (L101): o CI recusou o `sca: || true` frouxo do golden-path pelo `security` bloqueante do porto-os; o cofre trocou o token-em-texto-puro do prospix por `pgp_sym_encrypt`.
3. **Reuso = shape + conserto do buraco de segurança da fonte** — o custo de adaptação é real (des-Next-ificar UI, reescrever cliente de gateway, cifrar de verdade). Nunca é "de graça".
4. **1º uso escreve função pura (mesmo inline); 2º uso extrai para `_shared`** (L100) — extração vira alavanca (1 ponto de manutenção), cópia-de-padrão vira dívida (o kanban 3×).

### 20.4 · Reconcilie planejado × real (pós-mortem obrigatório — L101/L87)

O mapa de reuso é **hipótese**; a decisão só fecha ao tocar o código. No fim da sessão, reconcilie: o que foi copiado como planejado, o que virou **reescrita** (`@dnd-kit` → drag HTML5 nativo), o que foi **engavetado** (provisioning/white-label do cofecal/ponte). Meça o **efeito composto** (reuso-que-gera-reuso), não a contagem de peças. Sem a reconciliação, a hipótese vira "fato" herdado — a L87 no eixo de reuso.

### 20.5 · Devolva ao acervo (fecha o loop da L66)

Primitivos novos que se provaram nesta sessão voltam ao golden-path como **candidatos a template**: no FnC, o **cofre hardened**, `resolve_org_by_host`, `honesty.ts` (pós-filtro puro), `operation-sync` (fonte-de-verdade forward-only), o **capability-token** público, e a **parede-honesta / resolvedor de credencial de 3 camadas** (§14). O próximo e-commerce herda o testado — é a métrica de sucesso do método (L67): um padrão parar de ser re-derivado.

### 20.6 · A auditoria de SEAM (a fase que o reuso + a composição TORNAM obrigatória — L94)

Compor N peças testadas cria um risco novo: cada peça passa, o **elo** não. Ao final da integração, rode uma **fase de auditoria de seam** (fan-out de leitura, um agente por subsistema, **default = elo quebrado**) que traça o dado ponta-a-ponta atravessando as fronteiras: `checkout→pedido→produção→envio→rastreio→avaliação→recompra→financeiro`; `conversa→IA→curadoria→RAG`; `segmento→campanha/cadência→feed→CRM`. Procure os padrões da L94–L98: **dupla fonte-de-verdade**, **drift de enum + `.update()` mudo**, **dado órfão** (produtor-sem-consumidor), **gate ao-lado-do-caminho**, **preview×resolvedor divergentes**. É o §16 ("do demo ao real") com um passo a mais: **do "cada tela funciona" ao "as telas se falam"**.

### 20.7 · Ressalvas de honestidade do reuso (o relatório carrega estas)

- **"esforço evitado" é auto-declarado** (rótulo do mapa), não cronometrado; adaptação tem custo que a etiqueta esconde.
- **"referência de padrão" poupa design, não linhas** — nem todo item do mapa colou código.
- **planejado ≠ real** — parte foi reescrita ou engavetada.
- confie na **linha datada do ledger**, não no preâmbulo ("código é a verdade" vale **dentro** do doc — a L87/L88).

## 21. Migração de dados para um sistema VIVO + continuidade AI-dependente _(novo na v18)_

> Quando o trabalho **não** é construir um sistema, mas **encher e operar um já pronto** com dado real em volume — e o produto depende de um provider de IA que pode estar fora. As fases §A–§I continuam; §21 é o playbook específico dessa operação. É a **classe K** do catálogo (seed fura a lógica de app).

### 21.1 · A base é semeada; a INTELIGÊNCIA é derivada (L141/L142)
Separe **dois planos**: **base** (contatos/marcas/edições/vínculos — semeável por SQL, §21.2) e **inteligência** (fit/deals/tarefas/sugestões/engajamento/mentees — produzida por **IA + ação do usuário + triggers/crons/edges**; o `INSERT` SQL **fura os três** e a camada nasce morta). **Gate pós-carga:** audite as tabelas DERIVADAS (`count where fit_score is null`, `count(deals/tasks)`), não as de base. Zeros ali = inteligência apagada. Para cada derivado morto: dispare o gatilho no seed, **ou** crie o **trigger de banco** que faltava (L142), **ou** faça o **bootstrap determinístico** (§21.3).

### 21.2 · Seed idempotente (padrão portável)
Extrair por formato → **DRY-RUN** → **temp table + find-or-merge** por chave normalizada (colapsa acento+pontuação+**sufixo de status** — L147) → `INSERT WHERE NOT EXISTS` (cria) + `UPDATE coalesce(nullif(x,''),novo)` (enriquece, nunca sobrescreve) → filhas dedup por chave própria → **pré/pós count** → registrar no ledger → **dedup pós-import** (`having count>1 = 0`). Reexecutar = no-op. O parser **aprende por leva** (cada anti-padrão de dado humano vira função testada + redeploy — L147).

### 21.3 · Continuidade AI-dependente — o piso determinístico (L143)
Provider fora (429/sem-billing): **o piso não pode ser vazio nem constante.** (1) **Porte a heurística do produto para SQL** e preencha o backlog (ex.: fit = overlap de tokens marca×contato). (2) **Troque a constante do fallback da edge** pela heurística ("50 fixo" mascara a ausência). (3) **Feche o loop:** trigger enfileira → cron recomputa **sem** o provider → a IA **sobrescreve** quando volta. (4) Julgamento em massa (pessoa×empresa, profissão) → **subagentes Claude** (a cota do provider do produto não limita sua orquestração — L145, dual da L48). A IA é o *upgrade*; o piso é determinístico e **sempre presente**.

### 21.4 · Automação, bootstrap honesto e completude (L144/L148/L146)
Toda tarefa "automática" tem `cron.job` **ativo** (`select from cron.job`); per-org vira cron via wrapper `process-X-daily`. Seed de estado de negócio (deals) só de relações **reais** (`confirmed`), nunca fabricado. Campo obrigatório-de-produto: cobertura em camadas (fonte→determinístico→IA→**genérico honesto**), nunca inventando o específico. Dado esparso → **completude vira feature** (badge do que falta + popup de higiene). Enriquecimento externo: **notas primeiro, web 1-a-1 verificado** (L146). Ao mesclar com outro dev na main viva: **meça a coexistência** (L149).

**L56** _(QA)_ **Storage/privacidade não são seguros por default — classifique o dado.** Bucket **privado**; URL curta; anti-malware; **EXIF strip**; PII cifrada; **teste anônimo obrigatório**. _(Cofecal vazou XML fiscal por 4 buckets públicos.)_

**L61** _(QA, meta)_ **A esteira gera o esqueleto seguro, não o corpo operacional seguro.** O diagnóstico independente é o "retorno da realidade" que a filosofia exige: a v5 tinha a Fase H mas **consultiva**, e os projetos embarcaram com as lacunas. **v6 torna os gates de garantia bloqueantes, com evidência de runtime** — e reconhece que o **próprio NutriMatch** exibe vários gaps (localStorage, IA sem separação system/user, sem SCA/SIEM, storage não-auditado). _(A v6 listava também "idempotência não-atômica" — **rebaixado** na re-auditoria v13: o unique torna atômico, L86/L87.)_ _Garantia, não geração._

**L64** _(QA, causa-raiz)_ **Os gates derivam de um threat model, não de um checklist genérico.** Na Fase A: cada classe de dado (PII/fiscal/financeiro/mídia) → a superfície que a ataca → o gate §5B que a cobre. Sem isso, os 7 gates viram burocracia; com isso, viram cobertura da superfície hostil real do _seu_ produto.
**L65** _(QA, PONTE rate-limit)_ **Fail-open vs fail-closed é decisão declarada, nunca implícita.** Todo caminho de degradação de controle de segurança (rate-limit/assinatura de webhook/auth/IA fora do ar) **declara e justifica** a postura. **L66** _(QA, causa-raiz #2)_ **Defaults seguros pertencem a um scaffold, não a um doc.** A inconsistência entre projetos (storage público/privado-URL-longa/PII-texto-claro) é o sintoma de re-derivar segurança a cada projeto. **L67** _(cruzamento dos 4 post-mortems — v7)_ **Captura forte, propagação fraca: a MESMA classe de defeito recorre entre e dentro dos projetos porque a lição virou texto, não gate.** Cruzando os 4 QAs (Cofecal/PaP/EIV/PONTE — §19), **6 de 8 padrões são universais** (schema imaginado, dado fabricado, auth/tenant frouxo, renderiza-mas-não-funciona, só-o-browser-pega, gate-raso) — pegaram 3–4 produtos diferentes, feitos por agentes diferentes. **L70** _(cofecal R-072/R-071)_ **Build vermelho se tria — ambiente/cache vs. código — antes de virar gate FAIL; e limpar cache não é correção de performance.** Um `.next` corrompido (reparse point no Windows) ficou dias logado como "build FAIL" como se fosse regressão. (a) Build falhou → primeiro `rm -rf .next && rebuild`; só se persistir é código; **nunca commitar `.next`**. (b) O inverso também: build lento recorrente (>180s) **não se conserta limpando cache — faça profiling** (compilação vs page-data vs traces vs source maps). Cache-clear conserta corrupção, não lentidão.
**L71** _(cofecal R-073/R-075 — "erro nosso")_ **Chave pública ainda é JWT: hardcoded num workflow commitado, ela tripa o secret-scanner e o ruído mascara o vazamento real.** O `keepalive.yml` que propaguei aos 9 repos tinha a anon key (pública por design) **inline** — o scanner passou a dar FAIL crônico, e um FAIL que você aprende a ignorar é exatamente onde o vazamento real passa. **Regra:** nenhuma string em formato de token/JWT vive hardcoded em arquivo commitado, **mesmo pública** — roteie por `${{ secrets.* }}`; mantenha o secret-scan em **zero-match**, inclusive para matches benignos (senão o gate perde o sinal). Artefatos gerados (snapshots de review) **redigem** JWT antes de gravar.
**L72** _(cofecal, drift reverso)_ **Drift tem dois sentidos.** Uma migration aplicada no cloud sem arquivo versionado no repo (ledger à frente do disco) mente sobre o schema tanto quanto o inverso. O `check-drift` do scaffold compara os **dois** conjuntos (só-cloud **e** só-disco) — o gate não é "faltou aplicar", é "**repo ≠ cloud**", em qualquer direção.

**L73** _(pap-os, leva de remediação pós-auditoria — a L67 no nível do fix)_ **Uma leva de correção que não é guiada pela auditoria RANQUEADA fecha o fácil/visível e deixa o grave/invisível.** A 1ª leva de fix do PaP (4 commits, ~5k linhas, 8 migrations de RLS) fechou o que salta aos olhos — bypass de route-guard, rotas órfãs, policies de tela — e **deixou intactos os 5 críticos mais fundos**: edge `sol-chat` aberta (proxy anônimo de LLM + escrita cross-tenant), `has_permission` vazando entre redes, trigger de comissão comparando com enum inexistente (travava toda mudança de status do pedido), confirmação de negócio que nunca persistia (`.update()` em 0 linhas, mudo), `search_path` ausente em `SECURITY DEFINER` privilegiada. **A remediação é uma fase com DoD própria, não um respingo.** Gate: **cada correção referencia o ID do achado ranqueado**; o teste daquele achado **existe antes do fix** (a auditoria vira teste) e o CI o **re-roda**; a leva só fecha quando os **críticos** foram re-medidos como fechados. _Ataque o crítico primeiro; "mexemos naquela área" ≠ "o crítico fechou"._
**L74** _(pap-os)_ **O payload de um evento/outbox é um contrato — e o desalinhamento emissor↔consumidor falha em SILÊNCIO.** `criar_negocio_com_confirmacao` emitia `negocio.colocado` com `empresa_contraparte_id`, mas a reação em `process_events` lia `membership_citada_id` → a notificação "avisa o B" **nunca disparava, sem erro em lugar nenhum**. É a P1 (schema/contrato imaginado) na forma mais perigosa: **assíncrona e muda** (diferente do contrato de RPC/coluna, que grita PGRST202). Gate: **schema de payload compartilhado emissor↔consumidor** (não duas listas de chaves de memória); e o teste que **exercita a reação com uma linha real** (L22/§18) confere que a chave lida existe no payload emitido. Sem esse teste, o contrato mudo passa.
**L75** _(pap-os, amplia a L54)_ **`create or replace function` APAGA o `SET` da função — o `search_path` endurecido some silenciosamente na recriação seguinte.** No PaP, um `ALTER FUNCTION ... SET search_path` endureceu 12 `SECURITY DEFINER`; recriar depois `start_impersonation`/`provision_new_network` com `create or replace` **sem repetir o `SET`** teria revertido o endurecimento sem aviso — a config de `SET` não é preservada pelo replace. Gate: o lint de `search_path` roda **depois de qualquer recriação de função** (não uma vez só); toda `SECURITY DEFINER` recriada **re-inclui o `set search_path` no corpo** (o corpo é a fonte da verdade, não o `ALTER` avulso, que é frágil se o objeto for recriado adiante).

Prova, de novo, que o valor não está em capturar a lição, mas em **fazer o gate rodar** (L67): o `verify.sql` do PaP inclusive **pegou uma deriva pré-existente** (um teste anterior deixando `request.jwt.claims` setado) durante a leva — o gate funcionando como projetado.

**L76** _(ponte, leva de mecanismo — a L67 EXECUTADA)_ **Um padrão universal só para de reaparecer quando vira gate de código; e o PONTE foi a primeira vez que isso aconteceu de fato na esteira.** O "fetch manual a edge function" (P1/P6) reincidiu **2× dentro do próprio PONTE** (bug de marca → depois 4 hooks) porque a correção era pontual. O fix estrutural: **cliente único** (`apiCall` + `apiCallPublic`, com **parse defensivo** compartilhado), **registry tipado** (`EDGE_FUNCTIONS`) e **regra ESLint `no-restricted-syntax`** que **reprova o build** se alguém montar a URL `/functions/v1/` fora do único ponto sancionado (`api-client.ts`). **Prova por teste NEGATIVO:** um `fetch` cru num arquivo-isca **falha o lint** — testar que o gate BLOQUEIA o padrão ruim, não só que o código bom passa (o mesmo rigor do `verify` positivo+negativo). É a receita portável de L66/L67: para qualquer classe de invocação recorrente, entregue **um helper + um lint que bane a forma crua**, negative-tested, e ligue no golden-path/CI antes da 1ª entrega. _(Ganho extra: o parse defensivo do cliente único mata de uma vez o crash em resposta não-JSON que mascarava o erro real.)_
**L77** _(ponte)_ **Config/env capturado no LOAD do módulo congela antes do teste — leia em tempo de chamada.** `const BASE_URL = import.meta.env.VITE_SUPABASE_URL ?? 'localhost'` no topo do `api-client` é avaliado quando o módulo é importado — **antes** do `vi.stubEnv(...)` do teste rodar — então a URL saía com o **fallback**, o MSW não interceptava, e 4 testes quebravam de forma opaca. Fix: `function baseUrl(){ return import.meta.env... ?? ... }`, chamado na hora. Generaliza: **qualquer captura com efeito no topo do módulo** (env, `Date.now()`, singletons de config) congela um valor antes de o ambiente/teste poder ajustá-lo — prefira ler no ponto de uso. Também mais correto em produção (env pode mudar).
**L78** _(ponte, o inverso da L63)_ **O achado de uma auditoria/red-team também é ALEGAÇÃO — reproduza no runtime antes de corrigir; a reprodução pode REBAIXAR, não só confirmar.** A auditoria externa do PONTE marcou dois achados de alta severidade: "DoS por recursão infinita em `get_auth_org_id()` (Crítica)" e "race condition de idempotência financeira (Alta)". Reproduzidos no banco real, os dois **caíram**: (a) a "recursão" **não existe** porque a função é `SECURITY DEFINER` — o `SELECT` interno bypassa o RLS (provado: `count(*)` como `authenticated` sem a claim retornou sem _stack depth_); (b) a "race" está em **dead code** — `withIdempotencyKey` é usado por **0** edge functions (a idempotência real do webhook usa `UNIQUE`, atômico). "Medir, nunca confiar" **vale para o auditor também**: a L63 diz que a auto-auditoria é otimista demais (⇒ red-team obrigatório); a L78 é o outro lado — o red-team/auditoria pode ser **pessimista/errado**, e corrigir um achado não-reproduzido gasta a leva ranqueada (L73) no lugar errado. Corolário: um controle **safe por mecanismo não-óbvio** (o `SECURITY DEFINER` que quebra o loop) deve ser **comentado no código** — senão o próximo auditor re-flagra e o próximo dev "conserta" removendo o `SECURITY DEFINER`, aí **criando** o bug que não existia.

**L79** _(eiv, crise de deploy — a L51/L67 no eixo de OPERAÇÃO)_ **"Deployado" é um estado que se MEDE, não que se assume.** Numa auditoria de produção o EIV estava **no ar porém fantasma**: (a) o **auto-deploy GitHub→Vercel parou de publicar** — a prod ficou **~10 dias defasada** do `main`, com um deploy em `Error` que ninguém viu; o que se pensava "no ar" **não era o `HEAD`**; (b) **deep-link/refresh de rota profunda** (`/login`, `/app/…`) dava **404** porque o SPA rewrite não estava efetivo no deploy vivo — e **só a home abria**, então a navegação in-app nunca revelou (você entra pela `/` e navega por JS; ninguém dá F5 numa rota interna no teste). Nada disso é bug de código — é **operação não-medida**. O playbook **já previa** (§5.5 "confirme que o deploy REALMENTE rodou"; §13 "domínio aponta pro deploy novo"; §18 "cada rota abre") — **faltou rodar o gate** (L67 no eixo de ops). Gate: smoke pós-deploy que faz **GET cru** em `/` + `/login` + **rota profunda** na URL canônica (→ 200, não 404), **compara hash/idade do deploy vivo com o `HEAD`**, e falha em qualquer deploy `Error`. _"Medir, nunca confiar" vale para o **deploy**, não só para o código._
**L80** _(eiv, amplia L72)_ **Front e schema sobem JUNTOS — e a deriva dá pra medir só com a anon key.** O front no repo lia `produtos.imagens` e `loja_config.hero_presets`, mas **3 de 14 migrations estavam pendentes no cloud** → a query de catálogo daria **400** em produção. É o outro lado da L72 (drift repo↔cloud) com um acoplamento afiado: **deployar um front que depende de schema ainda-não-aplicado quebra a produção** tão certo quanto não deployar. Regra: meça `repo==ledger` **antes** do deploy do front; **migration primeiro (ou no mesmo passo), nunca o front à frente do banco.** Técnica barata (sem credencial admin): um `GET /rest/v1/<tabela>?select=<coluna>` com a **anon key** volta **400 `42703`/404 se a coluna/tabela falta** e **200 se existe** — rode a **query exata do app** contra o cloud e você sabe, antes de soltar, se o front vai 400. _(No EIV apliquei as 3 pendentes via Management API + registrei a `version` no ledger — L11 — e só então deployei.)_
**L81** _(eiv)_ **"Auth implementada" ≠ "alguém consegue logar".** O login real (Supabase Auth + RouteGuards) foi entregue e dado como pronto; em produção, dava `400 invalid_credentials`. Os usuários **existiam e estavam confirmados** no `auth.users` — mas a **senha do seed não era a documentada**. Um usuário confirmado com senha desconhecida **não é um login usável**; declarar "auth pronta" sem **logar em produção uma única vez** é a P3/P4 (fachada) no eixo de acesso. Gate: **smoke de login de produção** — `POST /auth/v1/token` com a credencial de **seed documentada** → **200 + JWT com o `perfil` certo** — roda antes de "pronto". Corolário: o seed de auth (usuário+senha por papel) é um **artefato versionado e testado**, não um valor lembrado; e **nunca resetar senha de usuário real** para "consertar" o teste — crie um usuário de teste dedicado.

> **Confirmação da esteira (L51/L67 pela 3ª vez, agora em OPS):** os três gates que teriam pego a crise do EIV — _"confirme que o deploy rodou"_ (§5.5), _"cada rota abre / repo==ledger"_ (§13/§18) e _"1 usuário por papel semeado"_ (fase E) — **já estavam no playbook**. O valor nunca esteve em capturar a lição, e sim em **fazer o gate rodar** — e a v11 estende o gate do **código** para o **deploy e o login**, os últimos metros até o cliente.

**L82** _(porto-os, delivery-ops — a L67 no eixo de GIT/ENTREGA)_ **PR empilhado + squash-merge fecha o PR-filho em SILÊNCIO e FORJA divergência de SHA fantasma.** As levas da Fase 2 do Porto OS vieram em PRs **empilhados** (a branch-filha = superset da `main`). Ao dar **squash-merge no `#5` e deletar a branch**, o GitHub **auto-fechou o `#6`** (financeiro, que tinha o `#5` como base) e — porque o squash reescreve o histórico num **único SHA novo** — o conteúdo do `#6` virou **idêntico ao da `main` mas com SHA diferente**, um _content-divergence_ que o `gh pr` lê como "nada a mesclar" ou conflito fantasma. Fix: **reabrir o filho com base na `main`** (`#8`), `git merge -s ours origin/main` nas branches-filhas (que já são superset da `main`) e então `gh pr merge`. Regra: **em PR empilhado, rebaseie o filho na `main` ANTES do merge do pai** (ou mescle em ordem sem deletar a base até o filho ser rebaseado) — `squash` + `--delete-branch` no pai **quebra o filho**. Gate: antes de deletar a branch de um PR que é base de outro, **rebaseie os filhos**; depois do merge, confira que cada PR restante ou fechou por **merge real** ou foi reaberto na base certa — _"auto-fechado" ≠ "mesclado"_.
**L83** _(porto-os)_ **Gating por PLANO/entitlement é um TERCEIRO eixo de authz — prove nos DOIS sentidos e semeie um dev-seed que LIGA o gated para testá-lo.** O Porto OS trava módulos por entitlement do tenant em **3 camadas** (filtro da nav, `RequireModule` na rota, **403 na edge**) — distinto do "gated por secret" (L37, que é custo-zero de infra) e do RBAC-por-papel (L44). Duas armadilhas: (a) **testar um módulo gated sem um tenant pago** exige um **seed de dev que LIGA todos os módulos** (a UI fica clicável localmente) enquanto o **seed de produção mantém o plano real** (Essencial) — senão o recurso nunca é exercitado antes de ser vendido; (b) o gate precisa de prova **nos dois sentidos** e em nível 3: módulo **OFF** → some da nav **E** rota bloqueada **E** edge 403 (não confie só no filtro da nav — é a L44/§14 "não confie só no RLS pra esconder tela", agora no eixo de **plano**); módulo **ON** (dev-seed) → as 3 camadas liberam. Gate: **entitlement testado ON e OFF nas 3 camadas**; o dev-seed que habilita o gated é **artefato versionado**, separado do seed de produção.
**L84** _(porto-os, amplia L79/L52 no eixo de OPS)_ **Um muro de autenticação na frente da produção (Deployment Protection/SSO) BLOQUEIA o próprio gate de bordas HTTP (5B-2) que você precisa medir em nível 3 — declare o gate BLOQUEADO-por-ops, não "OK".** O deploy de produção do Porto OS ficou atrás do **Deployment Protection da Vercel** (todo GET → **302 pro SSO**). Dá pra confirmar **HSTS/X-Frame-Options** no próprio 302, mas o **CSP/cookie por resposta real da app** (gate 5B-2, o **T3** do threat model) é **inalcançável atrás do muro** — a resposta que chega é a do SSO, não a da app. A tentação dupla a evitar: **nem marcar o CSP "OK"** (nunca foi medido — L52) **nem enfraquecer o controle** removendo a proteção sem autorização (L50, _security-weaken_). Postura correta: o gate 5B-2 fica em **nível ≤2 explícito, listado como "só o dono destrava"** (Fase H) com as três saídas possíveis — **bypass token de proteção**, **URL de preview sem proteção**, ou **domínio custom** — e o smoke de liveness (L79) roda contra a saída escolhida. Regra: **um controle de acesso que protege a produção também é uma barreira de MEDIÇÃO** — planeje **na Fase A** como o 5B-2 será medido através dele, senão o T3 embarca não-verificado **por construção**.

> **Confirmação da esteira (o padrão da L51/L67, agora pelo lado POSITIVO):** o Porto OS é o primeiro projeto **construído inteiro no caminho B2 (UI-first, L19)** a chegar num estado **limpo e provado em runtime** — sinal de que o golden-path/adapter trocável (L66) entrega quando os gates de fato rodam. E a lição-meta **inverte de sinal**: nas levas anteriores o playbook **já previa** os bugs que apareceram; aqui ele **preveniu** — os gates de consentimento/anti-PII/humano-no-loop **nasceram no design** e só precisaram ser **exercitados** (nível 3), não descobertos. O trabalho da sessão foi **medir**, não **remediar**.

**L85** _(nutrimatch, re-auditoria — a L51/L67 do lado do VERIFICADOR)_ **Auditar o invariante de banco com `grep` de texto é nível-2 e produz FALSO-POSITIVO — o gate roda contra o catálogo, não contra o `.sql`.** Ao avaliar o NutriMatch, contei `grep -c "security definer"` vs `grep -c "search_path"` por arquivo e achei "3 vs 1" no `0020` → quase reprovei `close_consultation` como não-hardened. **L86** _(nutrimatch, refina a L57)_ **UNIQUE na EXATA linha que o handler grava, dentro de 1 transação, É a guarda atômica de idempotência.** A L57 ("UNIQUE ≠ fluxo atômico") é verdadeira só em duas condições: o unique **não** cobre a linha escrita, **ou** o check-and-act (SELECT→INSERT) **cruza transações**. Dentro de **uma** transação de função com o `UNIQUE` na linha inserida, o banco **serializa e faz rollback do perdedor** — é atômico por construção. No NutriMatch, `create_first_consult` faz `if exists(select … asaas_payment_id) then return idempotent; … insert …` — parece o anti-padrão, **mas** `transactions.asaas_payment_id` é `UNIQUE` e a função inteira é 1 tx plpgsql: dois webhooks simultâneos com o mesmo `payment_id` → ambos passam o `exists`, ambos tentam `insert`, o **2º viola o unique e a função inteira aborta** (nenhum efeito parcial). O `exists` é só um **fast-path** para o retry sequencial. **Teste distintivo antes de "consertar":** _a unicidade é garantida pelo banco na linha que o handler grava, dentro de 1 tx?_ Se **sim** → seguro (ainda prove nível 4 com teste paralelo — a garantia é de desenho, não medida); adicionar advisory lock aí é contenção desnecessária. Se **não** (unique ausente, ou o write num statement/tx separado do SELECT) → é o ACH-06 de verdade. _(Cf. L78: o "race" do PONTE também caiu porque o unique real cobria e o `withIdempotencyKey` era dead-code.)_

Duas descobertas de método: (a) a varredura que **volta VAZIA é resultado positivo** (a mig 0024 registrou "nenhum irmão tem MFA/aal2" → autoriza greenfield; **registre a varredura negativa** senão o próximo re-varre o mesmo vazio); (b) o **complemento** (o que NÃO existe) é onde mora o esforço e o bug novo — emita "a lista de gaps" como artefato e **ligue cada gap ao threat model** (superfície nova, sem prova herdada). Delta: o playbook ganha a **fase de reuso (§20)** e o inventário-de-reuso como artefato do Dia 0.
**L100** _(flor-na-caixa, o efeito COMPOSTO do reuso)_ **A alavanca não é "copiar 33 coisas" — é que ~10 viraram PRIMITIVOS que se pagaram 2–6×; e "1º uso escreve função pura, 2º uso extrai" separa a alavanca da dívida.** Primitivos que renderam de novo NA MESMA sessão: `resolve_org_by_host` (nasceu p/ `store-catalog` → resolvedor tenant-por-host de `org-branding`+`frete-cep`+link de rastreio, 1→4); `org_secret_get`/cofre (→ Gemini, WhatsApp, Shopify, Brevo, Pagar.me, Judge.me, 1→6+); `_shared/cron.ts isCronAuthorized` (→ todos os crons + `finance-action` server-to-server); `honesty.ts` (Guardian do prospix → `ia-atendimento/guardrails` → **extraído** p/ `_shared` → reusado por `marketing-ideas` — cadeia externo→interno→re-interno); `whatsapp.ts loadCloudCreds` (→ 4 remetentes). **Contraexemplo que virou DÍVIDA:** o kanban foi **copiado** 3× (Produção→Envios→CRM) em vez de extraído para um `<KanbanBoard>` → 3 pontos de manutenção. Regra: distinga **extração** (1 fonte, barata — nasce quando o 1º uso já isolou uma função pura) de **cópia de padrão** (aceitável p/ UI divergente, mas paga N×); doutrina "**o 1º uso escreve a função pura mesmo inline; o 2º uso extrai para `_shared`**". Delta: o relatório de reuso mede o **efeito composto** (reuso-que-gera-reuso), não a contagem de peças.
**L101** _(flor-na-caixa, a L87 no eixo de REUSO)_ **Reuso = shape + conserto do buraco de segurança da fonte; quando as fontes divergem, escolha a MAIS HOSTIL (inclusive contra o próprio golden-path); e reuso PLANEJADO ≠ REAL — reconcilie.** Reuso quase nunca é "de graça": o cofre reusou o *shape* do `prospix` mas **trocou token-em-texto-puro por `pgp_sym_encrypt`**; o cron reusou a estrutura do `doavya` mas **trocou o JWT hardcoded pelo Vault**; o CI **recusou** o `sca: || true` frouxo do próprio golden-path pelo `security` bloqueante do porto-os. Regra 1: em peça multi-fonte, escolha pela **postura mais adversarial**, não pela fonte mais central — e marque "reuso = shape + correção do buraco da fonte". Regra 2: o mapa de reuso é **hipótese** — o `16-REUSO` planejou Kanban via `@dnd-kit`, e a realidade usou **drag HTML5 nativo** (`@dnd-kit` nem foi instalado); a decisão copiar/adaptar/reescrever só fecha ao **tocar o código**, e o pós-mortem **reconcilia planejado×real** (senão a hipótese vira "fato" herdado — a **L87 no eixo de reuso**). Também: eleja **UMA espinha** (base vs referência) por peça multi-fonte antes de escrever, senão funde modelos de dados incompatíveis.

**L102** _(flor-na-caixa, orquestração — refina L48/§0.5)_ **Fan-out de LEITURA é sempre seguro; fan-out de ESCRITA exige isolamento — e o gatilho de trocar de modo é FÍSICO, não estético.** O MESMO projeto provou os dois extremos: 6 agentes de **leitura** varreram 9 repos sem incidente e produziram o `16-REUSO`; o fan-out de **build** da wave 1 (3 edges + 8 telas em paralelo, commitando no mesmo working tree de um repo **sincronizado por OneDrive**) **contaminou o git** (staging cruzado, `git stash` escondendo trabalho alheio, OneDrive revertendo arquivos) — e a partir daí tudo virou serial (a memória de sessão datou a virada). Duas regras: (a) o §0.5 separa **fan-out de análise (use liberalmente)** de **fan-out de build (exige worktree próprio OU escopo disjunto + commit por pathspec pelo coordenador, agentes NÃO pusham)**; (b) **dimensione a onda pela DENSIDADE DE ACOPLAMENTO, não pelo nº de itens** — onda grande serve p/ fundação greenfield disjunta; costurar seams (envio↔pedido, recompra↔consent) colide no mesmo path e exige onda pequena e serial. Gate: modo "solo orquestrado" declara o pré-requisito de isolamento; **escrita concorrente em índice-git + pasta-sync compartilhados é anti-padrão nomeado**.
**L103** _(flor-na-caixa, orquestração)_ **O report estruturado do subagente É o CONTRATO da próxima onda; e "achado ≠ fix" mantém a onda atômica.** O padrão que fez ~20 ondas encadearem sem retrabalho: cada onda de backend **entregou o "contrato exato para o front ligar"** (nome/método/auth/body/retorno de cada edge) e a onda de front seguinte consumiu isso **literalmente** — o report do agente virou a interface, não prosa. E toda a leva manteve **achado ≠ fix**: bug fora do escopo (o `stop_if` da recompra achado pela onda de seam; os BUG#1/2/3 das auditorias) vira **item de backlog com ID + commit dedicado**, nunca patch inline no meio de uma onda de feature (preserva a atomicidade de que o ledger depende — é a L73 no eixo de escopo-de-onda). Delta: formalizar "report do agente = contrato tipado da próxima onda" e "achado→backlog com ID; fix é onda própria, referenciando o ID".
**L104** _(flor-na-caixa, evidência — o gêmeo do L84 para SEGREDO)_ **Existe um nível 3⁻ — "lógica real de produção rodada contra o CLOUD, com o hop HTTP final bloqueado pelo próprio harness" — e o classificador de segurança é um ATOR do processo.** Várias provas das G-waves/Grupo B rodaram a lógica real dos `index.ts` contra o banco N3 **porque o `x-cron-secret` do Vault foi bloqueado pelo classificador de segurança do harness** (não pôde ir num `curl`) — mais forte que estático (nível 2), menos que N3-HTTP puro (nível 3). Regra: quando o **próprio harness** barra a prova N3-HTTP (segredo em header, forjar JWT), o estado real é **3⁻** — "runtime de lógica real vs cloud, hop final bloqueado por ops/classificador"; **declare como 3⁻, não infle para 3 ✅** (gêmeo do L84, onde o muro de SSO bloqueava o gate 5B-2). Corolário: planeje **na Fase A como provar os controles gated-por-segredo** que o classificador vai barrar — senão embarcam em 3⁻ por construção; e trate o classificador como parte do **threat model do processo** (ele molda o que é provável).
**L105** _(flor-na-caixa, o padrão que destravou tudo — vai pro §14)_ **"Parede honesta / simulado fail-safe" é o default que permitiu N3 em ~toda integração SEM as credenciais reais do cliente — e o resolvedor de credencial em 3 camadas dá white-label sem flag-day.** ~10 integrações (Shopify, Pagar.me, Brevo, Omie, Judge.me, Google, WhatsApp, Gemini) seguem a MESMA postura: sem a credencial do cliente → `simulated:true` **honesto** (nunca "enviado/ok" falso), com o caminho **real provado contra o contrato oficial** via KAT/mock (openssl p/ o HMAC hex do Shopify, contrato Brevo, sandbox Pagar.me). Isso separou limpo **"código pronto"** de **"credencial pendente"** — e permitiu subir e provar o sistema inteiro antes das chaves. O lookup é cadeia de 3 níveis — **cofre por-org → env global → simulado** — que habilita rollout **incremental** de white-label (cada marca pluga o seu número/domínio sem quebrar quem usa o global), não um flag-day. Delta: elevar **"parede honesta + resolvedor de 3 camadas"** ao §14 (defaults seguros); é o par que torna "medir, nunca confiar" compatível com "as credenciais chegam depois".

> **Confirmação da esteira (a leva que abriu a 2ª dimensão do "medir" — o SEAM — e virou a 1ª esteira reuse-first):** as 9 levas anteriores endureceram **peça** (build/segurança/deploy) e **dado** (L88). O FnC prova que "medir, nunca confiar" tem um terceiro alvo: o **ELO** — o sistema passou em cada fatia e ainda estava desconectado (L94). E o padrão L51/L67 reapareceu dos dois lados: o playbook **preveniu** (a parede-honesta e o cofre nasceram do acervo, sem re-derivar — L99/L105) **e** foi pego de surpresa (o seam quebrado, que nenhum gate media — L94–L98; o reuso planejado≠real que ninguém reconciliava — L101). O antídoto é o de sempre, num alvo novo: **a testemunha independente** — aqui, o agente só-leitura que traça o fluxo cross-módulo com _default = elo quebrado_, o mesmo instinto da L63 aplicado à costura. _Medir, nunca confiar — inclusive no elo entre duas peças que, sozinhas, passam._

**L106** _(cjo-os, auditoria pré-produção — o SEAM/L94 virado GATE de go-live)_ **Antes de produção, rode uma auditoria ADVERSARIAL de N domínios em paralelo, cada achado ancorado em `arquivo:linha` + cenário de falha concreto + veredito — e a RE-auditoria CONFIRMA os fixes regenerando o gate, não citando.** No CJO OS pré-produção, 6 auditores (financeiro, fluxo comercial, segurança, loja, dados, **interação cross-feature**) acharam o que a revisão por-feature deixou passar: 1 CRITICAL (RLS ausente em `dedup_merge_log` → PII+custo pela anon key, dado real na mesa), 6 HIGH (as 3 corridas da L108, a comissão contada 2× no DRE, 2 buracos de dedup). O 6º domínio — **interação entre features** — é o SEAM (L94) institucionalizado como fase de auditoria permanente, não só na leva de costura. Regra: a auditoria **ranqueia por severidade**; a leva de fix **referencia o ID do achado** (L73); a re-auditoria **roda o gate de novo** (índice existe? policy on? função contém o marcador via `pg_get_functiondef`?), N3 no catálogo (L85), e devolve veredito PRONTO/COM-RESSALVAS/NÃO — nunca "revisei e tá ok".
**L107** _(cjo-os, a salvaguarda que te TRAVA é a salvaguarda FUNCIONANDO)_ **Um guard que você constrói pra impedir corrupção silenciosa VAI bloquear uma operação de cara-legítima depois — e isso é correto: fail-fast > `unique_violation` crua no meio do lote.** A leva de dedup-robusto (0153) adicionou uma salvaguarda que aborta com `UNIQUE_FK_SEM_CONSOLIDACAO` quando uma FK reassinalada cai num índice único COMPOSTO sem ramo de consolidação. Levas depois, o merge de fábricas **bateu nela** — porque outra leva (0151) tinha criado `unique(tenant,pedido,fabrica)` em `encomendas`. Não é regressão: é o sistema **se protegendo** de um merge que violaria a unicidade. Cura: **estender o ramo de consolidação** (espelhando estoque/reativacao_alvos) pra `encomendas`, não desligar o guard. Regra: quando surge um índice único composto novo sobre uma coluna deduplicável, o `dedup_merge` ganha o ramo antes do próximo merge; a salvaguarda que grita é preferível ao efeito parcial mudo (é a L96 "erro engolido" prevenida por desenho).
**L108** _(cjo-os, concorrência de DINHEIRO — a L57/L86 no eixo de MUTAÇÃO-de-dinheiro)_ **`check-then-act` sem lock, na criação de pedido/encomenda/recebimento, DUPLICA dinheiro — e as três recorreram no MESMO sistema.** Medido: `aprovar_orcamento` (SELECT sem `FOR UPDATE`, sem unique em `pedidos.orcamento_id`) → 2 cliques = **2 pedidos** + 2 reservas de estoque; `gerar_encomendas` (anti-dup por `NOT EXISTS`, sem constraint) → **2 contas a pagar à fábrica**; `receber_encomenda` (marcas de idempotência lidas ANTES do lock, nunca relidas) → **estoque + título a_pagar dobrados**. Fix = o par da L86: **índice único parcial na EXATA linha escrita** (`uq_pedidos_orcamento`, `uq_encomendas_pedido_fabrica`) + `FOR UPDATE` na linha certa + releitura da marca SOB o lock. Idempotência é comportamento (L57); no eixo de dinheiro, "rodar o handler 2×" não é log duplicado — é **passivo real**. Gate: todo RPC que cria dinheiro (pedido/título/comissão/encomenda) tem teste paralelo E o unique na linha que grava.
**L109** _(cjo-os, dedup — "mesma chave ≠ mesma entidade"; o gêmeo do L90 no eixo de MERGE)_ **Antes de MESCLAR dado real, meça a FORÇA DO SINAL da chave de match — e o campo DISTINTIVO que a chave ignora é a testemunha (L88).** No CJO: **CPF/CNPJ** (identidade legal) = seguro (42 grupos, **0 ambíguos**, nomes com typo confirmando). **Telefone/nome** = FRACO: 43 de 44 grupos ambíguos — um telefone com **23 clientes distintos** (número compartilhado), casal "KATIA E MARIO GOLONI", xará, e "RNI-RODOBENS / TERRA NOVA RODOBENS" (contatos da mesma construtora). **Produto por nome** = VARIANTE: dos 60 grupos curados iguais em nome+acabamento+preço, **100% tinham fotos DIFERENTES** = cores distintas; e os 7.505 "dups" restantes eram catálogo cru sem foto (placeholder que a loja não vende — L93). A prova de que não é duplicata é sempre o **distintivo que a chave textual não vê**: a foto (produto), a atividade e a similaridade real de nome (cliente). Regra: chave forte (documento legal) → merge; chave fraca (telefone/nome/nome-de-produto) → **artefato de revisão HUMANA**, não auto-merge. É o L90 ("meça antes de destruir") no verbo **mesclar**: mesclar pessoas diferentes é destruir a base. A **reversibilidade** (batch rotulado + `dedup_reverter`) é o que deixa dizer "sim" sem medo depois da revisão.
**L110** _(cjo-os, escopo — conheça o TENANT antes de agregar)_ **Uma query global de "duplicados" que não escopa por tenant MISTURA dois tenants → falsos duplicados + `TENANT_DIVERGENTE`; e o NOME do tenant ≠ a marca ≠ o escopo do dado.** O banco tinha DOIS tenants — **C.JÔ Acabamentos** (produção: 122 fábricas, 67k produtos, `f8e02c67…`) e **C.JÔ — Demonstração** (demo: 6/11/13, `0000…0001`). A varredura global de fábricas achou "Atlas ×2", "Leprê ×2" etc. que eram **um de cada tenant** — e o `dedup_merge` recusou com `TENANT_DIVERGENTE` (guard funcionando). Pior: uma auditoria anterior **confundiu o nome do tenant** ("Demonstração") com a **marca** ("Acabamentos") e reportou os números do tenant certo com o rótulo errado. Regra: **escope por `tenant_id` (ou `auth_tenant_id()`) ANTES de qualquer agregação/dedup**; registre qual tenant é produção; e nunca infira o escopo do NOME do tenant. _(Gêmeo de escopo da L110-cloud: o dado tem fronteira que a query precisa respeitar.)_
**L111** _(cjo-os, modele a estrutura, semeie o CONFIRMADO, torne o incerto CONFIGURÁVEL — a L92 no eixo de SEQUÊNCIA-DE-BUILD)_ **Money-code com inputs majoritariamente NÃO-confirmados: não encrave chute — construa o schema + a tela de config + o cálculo dos casos limpos, semeie só o confirmado, e deixe um FALLBACK seguro cobrir o resto.** A política comercial por fábrica tinha as %s pendentes (viriam por WhatsApp dos fornecedores). Em vez de cravar valores errados em linhas duplicadas, a leva entregou: `fabrica_formatos` (a ESTRUTURA), a TELA pra dona cadastrar, o cálculo dos formatos claros (comissão/sob-consulta 100%), e o **fallback "sob-consulta/manual"** pra qualquer fábrica não-configurada → **nada trava**, e o humano preenche na tela conforme a **autoridade** (o fornecedor) responde. O número é do dono/fornecedor (L92, "colete, não calcule"); a **estrutura** é sua. Regra: separe "estrutura pronta" de "número pendente" como a L105 separa "código pronto" de "credencial pendente" — o fallback honesto é o que permite subir a feature antes dos dados.
**L112** _(cjo-os, o dono escreve a FÓRMULA, delega a FIAÇÃO)_ **A função que DEFINE preço é do coordenador escrever e testar unitariamente; a UI e os RPCs de fiação fazem fan-out contra ela como contrato.** O `resolveFormatoPreco` (comissão = cliente paga a tabela e a C.JÔ ganha a %; revenda = custo+markup OU vende-no-sugerido; sob-consulta = manual) foi escrito à mão + **8 testes** ANTES de qualquer delegação — porque um preço errado é dinheiro (a irmã da L88/L89 no ato de CALCULAR, não só de guardar). Só depois o seletor por-linha (frontend) e o `aprovar/faturar` (backend) foram delegados a agentes, consumindo a função pura como interface (L103, "report = contrato"). Regra: o **núcleo de dinheiro** (a fórmula de preço/margem/imposto) é onde o coordenador NÃO delega — escreve, testa, e entrega como contrato tipado pra fiação fanout.
**L113** _(cjo-os, GUIAR em vez de travar — o nudge não-bloqueante)_ **Pra "deixar o dado do cliente 100%", um nudge que SEMPRE fecha, reaparece a cada login e some sozinho aos 100% bate um gate duro; e o score exclui o NÃO-aplicável senão a base parece 3% completa à toa.** O popup de completude (RPC `saude_dados` ao vivo → score ponderado + cards por gap, cada um com contagem e link pra tela) é dismissível (X/Esc/Depois/clique-fora), recorre no próximo login, e desaparece quando resolve — **nunca trava o uso** (era o requisito "à prova de leigo, mas dá pra fechar"). O oposto do bloqueio: orientar e se auto-limpar. E o denominador do score é "aplicável" — e-mail legado, `arquiteto_id`, o catálogo cru de 54k **não entram** (L88/L89: senão a base parece 3% completa por dado que a loja nunca vai preencher). Regra: complete-your-data é **guia recorrente e fechável**, não paywall; o score mede o que dá pra completar, não o que é N/A.
**L114** _(cjo-os, o formato do artefato = CANAL + AUDIÊNCIA)_ **Um documento pra LEIGO confirmar dado usa "é assim que funciona? + as perguntinhas" e some o jargão; e indo pro WhatsApp vira PDF, não link.** O doc pra os fornecedores confirmarem a política comercial mostra o entendimento atual em linguagem simples ("imposto (ST)", não "base de cálculo do ST"), pede **confirmar/corrigir ponto a ponto**, uma seção por fábrica — e foi gerado como **PDF** (pymupdf Story) porque a dona ia mandar no WhatsApp de cada uma (link HTML não cola tão bem num chat quanto um anexo). Regra: o **formato de entrega é parte do entregável** — case o artefato com quem lê (leigo → confirmar-ou-corrigir, sem jargão) e com o canal (WhatsApp → PDF/anexo). É o "à prova de leigo" da UI, no eixo de **documento externo**.
**L115** _(cjo-os, o classificador que barra a mutação é SINAL — L50/L90)_ **Quando o harness/classificador bloqueia uma mutação em massa de DADO REAL, a resposta é PARAR e confirmar a intenção com o dono, não contornar.** O classificador barrou o merge em lote de clientes reais; a leitura certa foi tratar como sinal (o dado é real e o sinal de match era fraco — L109), apresentar exatamente o que seria feito, e pedir o "sim" — não achar um caminho alternativo pra rodar. É a L50 ("autorize, não contorne") + a L90 ("meça antes de obedecer") no eixo de **mutação destrutiva de dado**; e a reversibilidade do batch é o que torna o "sim" seguro depois da confirmação. Corolário: separe a leitura (investigar/amostrar — sempre ok) da escrita (mesclar/apagar — confirmação explícita + reversível).

**L116** _(cjo-os, refina L91 — a tabela de AUDITORIA/LOG herda a sensibilidade do que fotografa)_ **Uma tabela que guarda `to_jsonb(linha)` como snapshot (log de dedup, auditoria, outbox) herda a SENSIBILIDADE do que fotografa — PII + custo — e a armadilha do `alter default privileges` atinge tabela NOVA: nasce com grant amplo a `anon`/`authenticated` e, se nascer SEM RLS, vaza.** O CRITICAL da auditoria foi `dedup_merge_log` (0126): `snapshot_loser jsonb` = a linha inteira do perdedor (cliente com PII, produto com `preco_custo`), tabela **sem RLS e com grant a anon** → `GET /rest/v1/dedup_merge_log` pela anon key devolvia tudo (123 linhas reais) + INSERT/UPDATE/DELETE (adulterar o log → envenenar o `dedup_reverter`). É a L91 materializada ("audite a TABELA, não só a função") + a armadilha da 0088 ("tabela nova volta a receber grant amplo"). Gate: **toda tabela de snapshot/log recebe a MESMA RLS da fonte** que fotografa; e uma **query de CI** lista qualquer tabela em `public` com grant a anon/authenticated e `relrowsecurity=false` → build vermelho (a classe de regressão vira gate portável — L67).
**L117** _(cjo-os, reconciliação — um valor que entra em DOIS caminhos conta 2×)_ **Um custo embutido num agregado E disponível como linha separada é contado em DOBRO — latente até a 1ª transação real; e um comentário de migration que PREVÊ a dupla-contagem é um TESTE não-escrito (L51).** No DRE, a comissão do arquiteto entrava no `cmv` (derivado de `pedidos.margem_real`, que já subtrai a comissão) **e** de novo em `despesas_variaveis` (o título "Comissão" tem grupo Vendas, que o DRE não excluía) → resultado subestimado em exatamente a comissão, por venda. Zero impacto no dia da auditoria (0 títulos de comissão) → **ativa no 1º faturamento com arquiteto**, o 1º dia de produção. E a migration 0065 **descrevia a armadilha em comentário** ("a dupla contagem nasce no primeiro pedido faturado"). Regra: quando um valor pode entrar por dois caminhos (embutido + linha), **exclua de um** com chave inequívoca (`comissao_id`); e um comentário que prevê um bug futuro é uma **asserção a virar teste**, não prosa (L51/L74).
**L118** _(cjo-os, lista HARDCODED em função de infra fica defasada em silêncio)_ **Uma enumeração fixa (FKs, colunas, tabelas) dentro de uma função de infra fica DEFASADA quando o schema cresce — derive do CATÁLOGO, não de uma lista cravada.** O `dedup_merge` reatribuía as FKs do perdedor por uma **lista fixa** por entidade; migrations posteriores adicionaram `devolucao_itens.produto_id`, `reaplicacao_historico.fabrica_id`, `fabrica_condicoes.fabrica_id`, `arquitetos.possivel_duplicado_de` — **fora da lista** → um merge deixaria essas FKs órfãs e o reverter não as restauraria, tudo mudo. Fix: derivar as FKs de `pg_constraint` em runtime (toda coluna com FK apontando pra entidade entra automaticamente). Regra: função de infra que enumera partes do schema (FKs, colunas de auditoria, tabelas por tenant) **lê o catálogo**, não uma lista hardcoded; se precisar da lista, um **teste que falha quando aparece uma FK/coluna nova não coberta**. É a L67 ("captura vira gate") no eixo de metadados-de-schema.
**L119** _(cjo-os, máquina de estados — valide a TRANSIÇÃO, e o ATALHO gera os mesmos efeitos)_ **Validar só o DESTINO de um status aceita retrocesso e saída de terminal; e um atalho que PULA um estado sem gerar os efeitos do caminho normal cria dívida INVISÍVEL.** Dois defeitos irmãos: (a) `atualizar_status_encomenda` validava a string de destino contra o enum mas **não o status atual** → dava pra ir `entregue → encomendado` ou sair de `cancelado`; cura = validar a **transição** (from→to), não o valor de destino. (b) `avancar_pedido_encomenda` ("já recebi tudo, liberar pra faturar") movia `a_encomendar → aberto` **pulando o fulfillment** — sem entrada de estoque, **sem gerar a conta a pagar à fábrica** → faturava com **receita e margem infladas e a dívida com a fábrica INVISÍVEL** (nenhum título a_pagar existia). Regra: transição de estado valida `from→to` explícito (terminais são terminais); e um **atalho que salta um estado** ou **produz os mesmos efeitos** do caminho normal (estoque + passivo) ou é **barrado** — um "pular etapa" que rompe o invariante contábil (receita sem o passivo par) é bug de dinheiro, não de UX.
**L120** _(cjo-os, conserte a MONTANTE — o import é a fábrica de duplicados)_ **Um import em massa sem idempotência (INSERT cego, sem match/`ON CONFLICT`, sem validação de documento) é a FÁBRICA dos duplicados que o dedup depois limpa a jusante — enxugar gelo.** A base tinha 40 grupos de CPF/CNPJ duplicado + 44 por telefone; a causa raiz é `importar_clientes` fazendo `INSERT` linha a linha sem dedup-on-import e **sem persistir o cpf_cnpj** (a chave forte de match), e `clientes.cpf_cnpj` sendo `text` **sem unique nem check**. O dedup (o `dedup_merge`) é o remédio a jusante; a cura é a montante: **dedup-on-import** (match por documento/telefone + `ON CONFLICT`) + **constraint de unicidade** (só depois de limpar a base — a limpeza é pré-requisito da constraint, L109). Regra: todo caminho de ENTRADA de dado (import, cadastro, API) tem idempotência e a chave forte validada — senão o dedup vira tarefa eterna. Corolário: você não cria a constraint numa base suja (ela falha); limpa (dedup) → depois trava (unique), nessa ordem.
**L121** _(cjo-os, staleness — invalide o FAN-OUT da mutação, não só a própria entidade)_ **Uma mutação que muda N agregados precisa invalidar TODAS as queries afetadas; senão o KPI na tela MENTE até um refresh.** `faturar_pedido` cria títulos, baixa estoque, grava margem, gera comissão e atualiza o cliente — mas o `onSuccess` invalidava só `['pedidos']`/`['pedido',id]`; o KPI "A faturar", o dashboard, o financeiro, o estoque e o DRE ficavam **stale** na tela pra quem já estava com elas montadas. Regra: mapeie o **fan-out** de cada mutação (o que ela toca no banco) e invalide o conjunto — `pedidos-resumo`, `titulos`, `financeiro-resumo`, `estoque`, `dre`, `painel-resumo`, `comissoes`, `clientes`. É a L94 (SEAM) no eixo de CACHE de UI: a peça (a mutação) funciona, mas o elo (a query que lê o agregado) não sabe que mudou. Gate: teste/checklist "após a mutação X, as telas Y/Z refletem sem F5".
**L122** _(cjo-os, runtime do cliente pós-deploy — a L69/L79 no browser)_ **SPA com PWA `autoUpdate` + chunks lazy, SEM ErrorBoundary raiz = TELA BRANCA pós-deploy.** Um deploy troca o hash dos chunks; um cliente com a aba aberta (ou o service worker servindo o precache antigo) pede um chunk que não existe mais → "failed to fetch dynamically imported module" → **sem ErrorBoundary, o app inteiro morre em branco, sem retry**. O CJO não tinha ErrorBoundary em lugar nenhum (`grep` = 0). Fix: ErrorBoundary raiz (fallback + "recarregar") + `lazyWithRetry` (recarrega 1× no erro de chunk, guardado em sessionStorage p/ não loopar). Regra: SPA com autoUpdate **exige** ErrorBoundary raiz + retry no import lazy — é a L69 ("warning tolerado = capacidade ausente") e a L79 ("deployado se mede") no eixo do **runtime do cliente**, o último metro.
**L123** _(cjo-os, o STUB que marca 'feito' sem entregar engole a fila — L47 no eixo cron/fila)_ **Um cron/handler que marca `enviado`/`processado` sem fazer a entrega ENGOLE a fila em silêncio — é a fachada (L47) na forma mais perigosa: perda MUDA de dado.** O `notificacoes-cron` marcava `agendada → enviada` com um `TODO(backend)` no lugar do envio real → toda notificação de cliente por canal externo (WhatsApp) era **silenciosamente descartada** (a fila drenava, nada saía). Fix defensivo: só marca `enviada` a de EQUIPE (in-app, que o sino de fato lê); a de CLIENTE fica `agendada` (não perde; entrega quando o sender existir). Regra: um consumidor de fila **não marca 'processado' o que não entregou** — se o canal não existe, **não consuma** (deixe pendente) ou marca só o que realmente saiu, distinguindo os canais. "Processado sem efeito" é a P3 (fachada) no eixo assíncrono, e some da vista igual ao contrato mudo da L74.
**L124** _(cjo-os, asset social — URL assinada expira; OG client-side é invisível ao scraper)_ **Um `og:image`/JSON-LD com URL ASSINADA que expira quebra o preview de link DEPOIS (o scraper cacheia); e OG injetado só client-side é invisível ao scraper (não executa JS) — a cura de ambos é server-side, e o padrão já existia no repo (reuse, L99).** A ficha de produto apontava `og:image` pra URL assinada de 24h (bucket privado) → WhatsApp/FB cacheiam no 1º scrape e o preview quebra em 24h; e o `<head>` era montado por `useEffect` (SPA) → o scraper via o `<title>Lojatta</title>` genérico. Regra: asset que vai pra meta-tag social precisa de **URL durável**; OG precisa ser **server-side** (bot não roda JS) — e cheque se o padrão já existe no acervo antes de escrever.
**L125** _(cjo-os, `INNER JOIN` numa listagem drop a linha de FK nula → o total não fecha)_ **Um `INNER JOIN` numa listagem some com as linhas de FK NULA (item avulso/serviço) — mas o TOTAL as inclui → a lista não bate com o total, e é pior numa tela PÚBLICA (o cliente vê a inconsistência e desconfia).** `orcamento_publico` fazia `join produtos` (INNER); um item avulso (frete/instalação, `produto_id null`) **sumia** da lista que o cliente vê no link, mas `subtotal`/`total` do cabeçalho **incluíam** o valor dele → o cliente soma os itens visíveis e não chega no total. Regra: listagem que tem um TOTAL agregado usa `LEFT JOIN` pra não perder linha (item avulso, produto merged/inativo); o `INNER JOIN` silenciosamente quebra a reconciliação lista↔total — e numa superfície pública isso é confiança perdida, não só bug.
**L126** _(cjo-os, rebrand por token não alcança hex CRAVADO)_ **Um rebrand por CSS-vars/tokens NÃO chega no que está com hex hardcoded no código — o resultado é meia-marca (a loja verde/rosa, o menu bege).** O white-label pintava as cores do tenant por CSS var no runtime, mas a sidebar e as pílulas usavam `#D8CCC0`/`#F0EAE3` cravados → o override da marca não os alcançava: a vitrine era da marca e o app parecia template. **L127** _(cjo-os, dado de SEED/DEMO polui relatório como real — identifique/prove/ISOLE, não apague)_ **Dado de simulação polui relatórios como se fosse real; identifique pelo PADRÃO tell-tale, PROVE que é demo antes de tocar, ISOLE reversível (não apague), e isole o CASCADE — e um tenant "Demonstração" separado é a forma limpa de não misturar.** A auditoria de integridade achou 11 pedidos que violavam o invariante "total = líquido": #3–#8 com os **itens somando SEMPRE 17.186** e o total **batido à mão** em valores redondos diferentes; #9–#13 com total redondo e **zero itens**; todos `origem null`, numeração baixa, clientes de persona de demo. **L128** _(cjo-os, meta — a auditoria enterprise ESQUECEU o texto; o cliente encontrou)_ **Seis auditorias cobriram código/segurança/dado/dinheiro/integridade/interação e NENHUMA olhou o que o usuário LÊ — a cópia (ortografia/gramática/formatação/consistência de rótulo/i18n) é uma superfície de primeira classe, mais ainda no idioma do cliente, e passou batido.** As auditorias foram fundo na RLS e no invariante do total; o CLIENTE viu o erro de acentuação na tela antes de qualquer coisa e perguntou "suas auditorias não pegaram isso?". **L133** _(flor-na-caixa, entrega · orquestração/worktree — refina L102)_ **Escrita concorrente de agentes num worktree sincronizado (OneDrive) injeta ARTEFATO de encoding (NUL bytes) em fonte VÁLIDA: o build passa, mas o arquivo vira "binário" pro grep/git.** Além de contaminar o índice-git (L102), duas ondas paralelas gravaram bytes de controle no meio de um `.tsx` (um agente usou `\x00` cru como separador de uma chave de detecção de mudança) — `tsc` e `vite build` toleraram, mas o `git` passou a ver o arquivo como binário e o `file` reportava "data" num `.ts`. **L167** _(cjo os, SEAM/DRY — fonte-de-verdade ÚNICA do que o CLIENTE vê; gêmeo da L94/L100 no render client-facing)_ **Tudo que o cliente lê nasce de UM componente presentacional.** O `PropostaView` (sem custo/margem/comissão por construção) alimenta os QUATRO: a prévia da Etapa 5 do wizard (estado ao vivo), o **Modo Apresentação** (tela cheia pra virar ao cliente), a **rota pública** `/orcamento/:id`, e é espelhado pelo **PDF** — então o que o cliente vê ao vivo é IDÊNTICO ao que recebe, e não viram 4 designs que divergem. **Regra: saída client-facing (proposta, recibo, espelho) tem UM componente-fonte; live/tela-cheia/público/PDF são RENDERS dele, nunca cópias** — e o "nunca vaza número interno" prova-se UMA vez, na fonte. Antes de construir uma 2ª visão do mesmo documento, reuse a fonte ([[L164]]/[[L100]]).

**L168** _(cjo os, AUTHZ — DELETE destrutivo por UMA regra, num RPC; refina §5.3/§14)_ **Para uma operação destrutiva ser single-role e single-rule, BLOQUEIE o DELETE direto com policy RESTRICTIVE `for delete using(false)` e roteie TODO delete por UM RPC `SECURITY DEFINER` que carrega a regra** (checa o papel via `auth_role()`, recusa linha com histórico a jusante — aprovado/virou-pedido — e faz o cascade). A RLS de tenant costuma ser `for all` PERMISSIVA → o DELETE fica aberto a qualquer perfil do tenant; a policy restrictive (AND-ada) fecha, e o RPC (definer, fora da RLS) vira o **único ponto** onde a regra vive. Testado por papel via L160. **Regra: op destrutiva com regra ≠ trivial → restrictive-`false` na tabela + RPC-definer como porta única; a regra mora em UM lugar, provada por papel; nunca apague linha com histórico a jusante.**

**L169** _(cjo os, SQL + CONTENÇÃO — troca de linhas sem drift, E quando NÃO construir o transacional)_ **`jsonb_populate_recordset(null::minha_tabela, payload)` mapeia jsonb→linhas pelo ROW TYPE da tabela — troca em massa (delete+insert numa função = 1 transação) SEM repetir a lista de colunas** (o cast tipa sozinho; só o `INSERT (col...)` explícito, pra deixar `id`/`created_at` no default). MAS a lição-irmã é de **contenção**: eu construí esse RPC transacional pro autosave e **decidi NÃO usá-lo** — o autosave frequente **se auto-cura** (o próximo tick reescreve), então reusei o caminho de save já provado (`atualizarCompleto`), evitando um **mapeamento de colunas PARALELO que dá drift** a cada coluna nova do wizard. **Regra: a técnica transacional existe e é limpa (row type, sem drift), mas um caminho FREQUENTE que se auto-cura não precisa de atomicidade estrita — reusar a mutação provada > manter um 2º mapeamento; construir o robusto quando o custo de drift > o ganho de atomicidade.** (A garantia forte fica pro save MANUAL, raro; o auto, self-healing.)
